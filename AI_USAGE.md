# AI usage

How AI tools were used to build FITSCAN, what the developer decided and checked, and where the limits are.

## Tool

FITSCAN was built with **Claude Code** (Anthropic's AI coding assistant, running Claude models) in the developer's
editor and terminal. Every commit carries a `Co-Authored-By: Claude Opus 5.5` line. No AI service is used **by** the
application at run time: matching is a weighted formula, with TF-IDF (scikit-learn) only to order equal scores, and
industries come from explainable rules.

**Authorship.** The code, tests and documentation in this repository were generated by the assistant. The
developer's part was the direction, the decisions listed below, and the review and approval of every change. The
code is not presented as hand-written by the developer.

## How the work was organised

The project was built in phases (setup, database, crawler, resume parsing, matching, search and exports, landing
page, application UI, optional features, real job sources, final integration). Each phase followed the same loop:

1. **The developer set the scope and constraints**: what to build, what not to touch, and safety rules (no real
   crawls, uploads or full recomputations without approval; never reset the database; no commits without approval).
2. **The assistant audited the code and proposed plans and options**; the developer approved, changed or rejected
   them. Decisions the developer made include: the edge-case rule for jobs without skills (no skill points),
   adjustable weights as whole numbers that must add up to 100, automatic re-matching with an off switch
   (`AUTO_REMATCH`), the brand palette and page design, no "AI-powered" wording, privacy rules for logs and upload
   responses (upload IDs, never file names or personal details), which optional features to build or defer, and
   which live crawls to run.
3. **The assistant implemented** code, tests and documentation, ran the tests and checks, and reported the results,
   including failures and anything skipped.
4. **The developer reviewed** each report and diff, then approved the commit and the push.

## What the assistant did

- Drafted the HLD, LLD and architecture decisions from the brief, then the code that implements them.
- Wrote the backend (FastAPI, SQLAlchemy, Alembic, Celery), the crawler and extractors, resume parsing with OCR, the
  matching engine, the frontend (React, Tailwind CSS, shadcn/ui), Docker Compose and the CI workflow.
- Wrote the automated tests and the offline fixtures (invented companies and people), and ran browser checks against
  a contract mock of the API and read-only checks against the running application.
- For the submission: recalculated the five-candidate hand check from the database, produced `samples/` with
  FITSCAN's own export code from stored results, investigated database activity read-only, and drafted the README,
  `DATA_SOURCES.md` and this file.
- For the public deployment (23–24 November): wrote the Caddy proxy, the production Compose override, the
  environment check and the backup script and timer; worked on the production VM over SSH, with each disruptive step
  approved by the developer (deploys of single services, a reboot test, backups, the demo-data crawls); audited the
  live site (read-only browser runs through an SSH tunnel, an independent recalculation of every stored match) and
  fixed the defects found, each with a regression test.

## How the output was checked

The assistant ran these checks and reported the results to the developer:

- **Automated tests**: 1,158 backend tests in the latest CI run (unit and PostgreSQL integration, run against a
  separate `matching_test` database), the TypeScript build, a sidebar rendering check, and GitHub Actions on every
  push.
- **Mutation checks** for safety rules: deliberately broken copies of the code (for example without the match-queue
  lock or without the demo-site guard) were run to confirm the tests catch the defect.
- **Live checks** against the running stack: read-only browser runs that block every write request, database
  snapshots before and after, a database backup before migrations, and two small approved live crawls (20 jobs).
- **Hand checks** recorded in the README: the top 3 jobs of five candidates, recalculated from the database and
  compared with the stored scores. The README also says where those rankings do not make sense.

## Data and privacy

- Test data is synthetic: invented resumes (`backend/tests/resume_pdfs.py`) and invented companies in the job-board
  fixtures. No real resume is in the repository, and `samples/` and the README use only synthetic candidates.
- Logs never contain resume text, names or contact details; uploaded files are stored under random IDs.
- The assistant worked on the developer's machine and, for the deployment, on the production VM over SSH; secrets in
  either `.env` were not printed or committed, and checks compared secrets with logs only as counts, never values.

## Limits

- The developer is responsible for the final result and for explaining all of it. The AI-generated code and text
  were checked through the reports, diffs and tests above.
- Industry classification and skill extraction are rule-based: they are explainable and tested, not perfect. The
  README's hand check shows false skills read from a real posting.
- Live crawls covered Fake Python Jobs, the mock site, one Greenhouse board and one Lever board. Company career pages
  are verified only with a saved test page: the one live attempt (Shopify careers) found no jobs.
